# 静默技术调研

这一步产品经理看不到过程，也不需要看懂。目的是让你的追问基于系统事实，而不是凭空设想。

## 1. 先读项目说明（存在哪个读哪个）

- `AGENTS.md`、`CLAUDE.md`、`README.md`
- 规格文档目录：如 `openspec/specs/`、`docs/`、`specs/`
- `prd/` 下已有的 PRD（避免和已有需求重复或冲突）

项目说明里的约束（如"某类功能暂不做"、权限模型、开发流程）对本需求同样有效；冲突时要告诉产品经理。

## 2. 定位需求落在哪

- 用需求里的业务名词搜索代码和文档（中文名词、可能的英文名、页面标题、菜单文字）。
- 找到相关的页面、接口、数据表/模型、权限判断。
- 只读不改，不运行会改数据的命令。

## 3. 把业务名词映射到系统事实

对需求里的每个关键名词，查清：

| 要查的 | 为什么 |
|---|---|
| 系统里有没有这个东西 | 没有的话是新建，工作量和影响完全不同 |
| 系统里它的含义是否和产品经理说的一样 | 例如产品说的"部门"是否包含子部门 |
| 它和其他东西是一对一还是一对多 | 例如一个员工能不能同时属于两个部门 |
| 现有的谁能看/谁能改规则 | 新需求经常无意中扩大或缩小了权限 |
| 现有数据有没有空值、历史遗留情况 | 决定"历史数据怎么办"要不要问 |

## 4. 产出（分两处用）

**对产品经理说的（大白话）：**
- 系统现在相关的功能是怎样运作的（3～5 句）
- 需求会影响到哪些现有功能
- 发现的冲突，以及需要对方拍板的点 → 转成第 2 步的问题

**写进 PRD「开发附录」的（技术语言，给开发看）：**
- 相关代码位置（文件路径，能定位到函数更好）
- 相关规格文档
- 你查到的技术事实与依据
- 你查不清、需要开发确认的技术问题（例如"现有数据是否都有部门字段，空值比例未知"）

## 5. 纪律

- 说出的每条系统事实都必须来自你实际读到的代码或文档；没读到就说"未确认"，不要编。
- 调研是为了提更好的问题，不是为了设计技术方案。PRD 里不写实现方案，最多在开发附录里写"可能涉及的位置"。
- 仓库很大时，只查和本需求相关的部分，不要通读全仓库。
