# PRD 模板

按下面的结构生成。不适用的小节保留标题，写"不适用：<理由>"，不要删掉。
`<>` 里是填写说明，生成时替换掉。

---

```markdown
# <需求名称>

| 项目 | 内容 |
|---|---|
| 状态 | 草稿 / 待补充 / 可开发 |
| 提出人 | <产品经理姓名> |
| 日期 | <YYYY-MM-DD> |
| 期望上线 | <日期及原因；没有写"无硬性要求"> |
| 澄清进度 | 已确认 <n> 项 / 不适用 <n> 项 / 待定 <n> 项 |

## 1. 背景与要解决的问题

<现在怎么做；痛点；谁在痛。用事实，不用"提升体验"这类空话。>

## 2. 目标与成功标准

<上线后如何判断做成了。尽量可度量，例如"HR 每周手工整理表格的时间从 2 小时降到 0"。>

## 3. 范围

### 3.1 本次要做

1. <能力 1>
2. <能力 2>

### 3.2 本次不做

- <明确排除的内容>（原因：<为什么不做 / 以后再说>）

## 4. 使用者与入口

| 角色 | 在哪里用 | 做什么 | 量级 |
|---|---|---|---|
| <角色> | <端 / 页面 / 按钮> | <操作> | <人数、频率、数据量> |

## 5. 主流程

<按步骤编号写，每步写清"谁做了什么 → 系统做了什么 → 用户看到什么"。复杂时可附流程图（mermaid）。>

## 6. 业务规则

| 编号 | 规则 | 例子 |
|---|---|---|
| R1 | <判断条件 / 计算口径 / 统计方式> | <一个具体例子> |

|---|---|---|---|

|---|---|---|---|---|

| D4 | 撤回与修改 | |

| D6 | 多人同时操作 | |
| D7 | 失败、超时、无人处理 | |
| D8 | 上线前的历史数据 | |

## 8. 权限

| 角色 | 能看到什么 | 能做什么 | 不能做什么 |
|---|---|---|---|

敏感信息处理：<哪些信息敏感、如何处理；没有写"不涉及">

## 9. 对现有功能的影响

| 现有功能 | 现在的行为 | 上线后的行为 | 产品经理确认 |
|---|---|---|---|

## 10. 通知与记录

- 通知：<给谁、什么时候、什么渠道、内容要点；不需要写"不需要">
- 操作记录：<需要记录哪些操作；不需要写"不需要">

## 11. 验收标准

每条用"当……时，系统应……"的句式，必须能被人实际操作验证。

| 编号 | 验收标准 | 对应规则/边界 |
|---|---|---|
| AC1 | 当 <前提和操作> 时，系统应 <可观察到的结果>。 | R1 |

## 12. 上线方式

<一次全员 / 先试点哪些人；历史数据处理方式；是否需要提前通知用户。>

| 编号 | 问题 | 谁来回答 | 截止时间 |
|---|---|---|---|
```

## 完整度自检（生成后逐项检查，不写进 PRD）

- [ ] A、B、C、D、E、G 组必问维度全部是"已确认"或"待定"，没有静默跳过的
- [ ] 第 3.2 节"本次不做"不是空的（真的什么都不排除，要写明"无"并说明原因）
- [ ] 第 7 节八种边界情况每一条都有答案或"不适用：理由"
- [ ] 每条业务规则至少有一个具体例子
- [ ] 每条验收标准都是"当……时，系统应……"，且能被人实际操作验证
- [ ] 每条业务规则和边界情况至少被一条验收标准覆盖
- [ ] 正文里没有模糊词：快速、及时、友好、合理、适当、尽量、等、之类、大概、一般情况下、支持各种
- [ ] 正文（第 1～13 节）里没有技术术语和代码；技术内容只在第 14 节
- [ ] 所有"推荐答案"都已得到产品经理明确确认，没有你替对方拍板的
- [ ] 文档状态与待定事项数量相符
